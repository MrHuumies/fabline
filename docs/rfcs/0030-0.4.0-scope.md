# RFC 0030 — 0.4.0 scope: demand-driven production

- **Status:** proposed
- **Author:** FABLINE
- **Date:** 2026-11-26
- **Related:** [0.3.0 coverage review](../coverage-review-0.3.0.md),
  [`factory-v0.2`](../../benchmarks/factory-v0.2/card.md), RFC 0029, ADR 0041
- **Approved by:** pending owner review

## Summary

0.4.0 proposes **one integrated mechanic**: demand-driven multi-item
production. A second intermediate item and alternative recipes create a real
product-mix decision; a seeded order stream with quantities, deadlines, and
values turns that mix into planning and control under demand.

The release also adds a **deep/offline RL baseline track** on the new control
task and considers a **generative recipe pilot** on the richer recipe space. A
new `factory-v0.3` benchmark is a candidate, not a commitment; it is frozen only
after the pilots pass.

This is intentionally not a grab bag. Decentralized variants, more calibration
views, and generative models on the current seven line grammars are out of
scope.

## Why this scope

0.3.0 closed several lines:

- true-simulator planning is positive, but learned value, one-step transition,
  uncertainty-ensemble, and two-step transition models are negative or shallow
  (0076, 0083, 0085, 0086);
- decentralized local policies are retired (0081, 0082);
- fault calibration is positive, maintenance calibration is mixed, and power
  calibration is near majority (0078, 0084);
- causal removal is a task-level positive (0079);
- the generative feasibility audit is negative: 7 unique line sequences and
  diversity 0.080 (0087);
- the efficiency table and viewer QoL are complete (0088 and the wizard/
  browser commands).

The remaining gaps are structural:

1. **No combinatorial production decision.** The line makes one product with a
   fixed recipe; product mix, alternative recipes, and order value are absent.
2. **No demand-side uncertainty.** There is no order stream, deadline pressure,
   or price/value trade-off.
3. **Deep/offline RL has no non-toy control task.** Tabular Q and behavior
   cloning are the only control baselines.
4. **Generative work has no content to generate.** The line grammar has only
   seven semantic outcomes.
5. **World models have a representation ceiling.** More varied production
   structure gives transition models a harder but richer problem.

A multi-item production tree addresses all five at once. An order stream is a
task layer on that tree, not a separate world.

| Energy storage + intermittent power | charge/discharge, reserve, ramp | control, planning, calibration | medium; power line already broad; risk of another scripted puzzle | fallback |

## Recommended scope

### Mechanic — multi-item production tree

An opt-in `ProductionConfig` adds a small recipe graph:

```text
ORE -> INGOT                    (furnace)
INGOT -> COMPONENT              (assembler, one alternative recipe)
INGOT + COMPONENT -> GEAR       (assembler, current output)
INGOT -> GEAR                   (slow alternative, optional)
```

The exact recipe set is fixed by the task card, not a content treadmill. The
goal is a **product-mix decision**, not many new items:

- at least two intermediate/output recipes with different cost and throughput;
- a recipe switch that costs setup time;
- no new world, renderer, or dependency.

The default world and `factory-v0.1`/`factory-v0.2` hashes remain unchanged when
the opt-in config is absent.

### Task layer — seeded order stream

An opt-in `OrderConfig` adds:

- orders with item, quantity, deadline, and value;
- a deterministic seeded arrival schedule;
- fulfillment on delivery, with late/unfilled penalties;
- an `orders` observation view and order events in the state hash.

The order stream is a task layer, not a second physics system. It turns the
recipe graph into a planning/control problem with deadlines and value.

### Candidate tasks

1. **Order planning** — choose an initial recipe/line configuration for a known
   order set; compare scripted, CEM/planning, oracle, and random.
2. **Order control** — switch recipes and build/route to meet deadlines; compare
   scripted EDF/value, tabular Q, BC, PPO/SAC (optional Torch), and random.
3. **Demand calibration** — predict late/unfilled risk and order value; Brier,
   NLL, ECE, with a skill gate before calibration is read.
4. **Recipe intervention** — remove or switch a recipe and predict the
   counterfactual production/order effect; causal task variant.
5. **Generative recipe space** — generate valid recipe graphs/lines; only after
   the recipe grammar is shown to have enough structural diversity.

### Baseline track — deep/offline RL

- PPO and SAC on order control, with the existing Torch optional extra.
- Behavior cloning from scripted/EDF and human demos.
- Tabular Q and scripted policies as compute-cheap references.
- Report sample/compute/inference cost alongside score; no leaderboard claim.
- No new dependency: Torch remains optional and the core stays NumPy/stdlib.

### Benchmark

- `factory-v0.2` remains immutable.
- A `factory-v0.3` candidate may add order planning/control and one causal or
  calibration task **only if** the pilots pass.
- Freeze requires 20 test and 20 shift/layout episodes, expected summaries, and
  CI checks. If the pilots do not stabilize, 0.4.0 ships without a new frozen
  benchmark.

### QoL

- No new GUI scope. Keep the wizard, replay browser, and task-card viewer.
- Any viewer additions remain read-only and optional.

## Phases and gates

| Phase | Work | Gate |
|---|---|---|
| 0 | RFC/ADR, `factory-v0.3` draft spec, task cards | owner approval |
| 1 | Multi-item production tree | opt-in; default hash unchanged; 5-seed throughput/recipe pilot |
| 2 | Order stream + order planning | 5 seeds; scripted/oracle gap; no saturation |
| 3 | Order control + deep/offline RL | 5 seeds; learned baseline beats random; success gate |
| 4 | Demand calibration / causal intervention | skill + calibration/intervention gates |
| 5 | Generative recipe pilot (optional) | ≥20 unique recipe structures; diversity ≥0.25 |
| 6 | Benchmark candidate | stable tasks, expected summary, CI |
| 7 | Release audit | clean export, assets, docs |

A phase that misses its gate is reported negative and does not enter the frozen
benchmark.

## Quality gates

- Every new mechanic has an ADR and tests.
- Every task has a card and a pre-registration.
- Every task uses at least five seeds for the pilot; benchmark freeze needs 20
  test and 20 shift/layout episodes.
- Default `factory-v0.1` and `factory-v0.2` hashes remain unchanged.
- No new dependency without an ADR; Torch stays optional.
- No task is promoted if its baseline ordering is saturated or unstable.
- No viewer code mutates state.

## Non-goals

- a new world, 3D, fluids, trains, or full circuit networks;
- another decentralized representation or critic variant;
- another calibration view on the current content;
- a generative model on the seven current line grammars;
- deep RL from scratch as a new mechanic (baselines only);
- PyPI/Zenodo publication;
- a new frozen benchmark before the pilots pass.

## Risks

- **Content treadmill.** The recipe graph must stay small and decision-focused;
  if it grows into a content catalog, stop.
- **Action-contract churn.** Recipe switching needs a clear action and state
  contract; changing the frozen action space is not allowed. Use an opt-in action
  or task wrapper.
- **Deep RL compute.** PPO/SAC can be expensive; keep budgets small and report
  cost, or run them as an optional baseline track.
- **Order tuning.** Deadlines/values could accidentally make a scripted rule
  optimal; preregister the regime and report if the oracle gap is shallow.
- **Benchmark scope creep.** Freeze only tasks that pass; 0.4.0 may ship without
  a new benchmark.
- **Generative overreach.** The recipe grammar must be audited for structural
  diversity before a generative task is added.

## Alternatives considered

- **Energy storage as the flagship.** Smaller, but the power line is already
  broad and risks another scripted scheduling puzzle. Keep as fallback.
- **Quality/rework as the flagship.** Good uncertainty axis, but the calibration
  line is already mixed and the decision is narrower than product mix.
- **Richer layout grammar only.** Directly fixes generative feasibility but adds
  little planning/RL coverage; use as an optional phase.
- **Deep/offline RL only.** Adds baselines but no new decision surface; retain as
  a baseline track.
- **No new mechanic; efficiency/QoL only.** Not enough research coverage for a
  minor release.

## Decision

**Proposed, pending owner approval.** On approval:

1. write ADR 0042 for the 0.4.0 scope;
2. write the `factory-v0.3` draft spec and task cards;
3. implement the opt-in production tree and order stream;
4. run the pilots before any benchmark freeze;
5. keep `factory-v0.2` immutable.
